# 探针调试工作流

## 何时用探针

| 场景 | 工具 |
|------|------|
| 查当前状态（坐标/NBT/背包）、验证 API 返回 | execute_code 实时查询（「游戏内执行代码」skill） |
| bug 只在真实事件链路中发生（点击/骑乘/UI 操作的瞬间）、偶发复现、时序依赖；实时查同样代码却正常 | **探针**：记录代码埋进事件链路，用户复现后读日志分析 |

实时查询正常但业务时刻异常 → 入参或上下文在业务时刻就错了，这类只能靠探针。

## 探针写法

模块级 DebugLog 写文件，**不要用 print**（游戏日志窗口滚动快、双端混流、拿不到历史）：

```python
import os, time   # 缺哪个补哪个

PROBE = os.path.join(os.environ['TEMP'], 'probe.txt')

def DebugLog(tag, data):
    with open(PROBE, 'a') as f:
        f.write('%.3f %s %s\n' % (time.time(), tag, data))
```

客户端文件同路径，tag 加 `C_` 前缀，时间戳对齐双端时序。

记录一律 `%r`/`repr`：`'-1'`（字符串）、`-1`（数字）、`None`、`[]` 是四种不同的静默失效形态，str 化后无法区分。

## 埋点原则

1. 链路两端 + 中间判定点：客户端发什么（原始 args repr）、服务端收什么、每个判定依据的原始值；数据从哪一环开始对不上，根因就在哪一环
2. 循环体入口打一条：零输出 = 集合/查询本身是空的，直接排除循环体内部逻辑
3. 信息不足就加密探针让用户再复现一次，不要无数据时反复猜测

## 流程

```
1. 删探针文件（只留最新一次现场）
2. 双端埋探针 → hot_reload
3. AskUserQuestion 给完整操作路径（如"坐上座位→右键控制台→点启动"），选项覆盖复现成功/没复现/成功
4. 读日志，按时间戳对齐双端时序分析
5. 定位根因 → 修复 → 用户验证
6. 删全部探针（含 import、PROBE、DebugLog 函数、调用行）→ grep "DebugLog|probe" 验证无残留 → hot_reload → 删探针文件
```

复现失败也是信息：对比两次日志中链路数据的差异。
